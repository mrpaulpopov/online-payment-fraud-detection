# Обнаружение мошенничества с онлайн-платежами (Online Payment Fraud Detection)
![CI](https://github.com/mrpaulpopov/online-payment-fraud-detection/actions/workflows/ci.yml/badge.svg) Русская версия | [English version](README.md)

Полноценный (end-to-end) MLOps пайплайн для выявления фрода в реальном времени, основанный на датасете IEEE-CIS Fraud Detection.

Я разработал и оптимизировал (с помощью Optuna) две модели: baseline LightGBM и гибридную PyTorch Autoencoder + LightGBM. Метрики MLflow показали, что автоэнкодер отработал намного лучше на обучающей выборке, что говорит о начале переобучения. Однако на тестовой выборке он дал лишь крошечное улучшение нашей ключевой бизнес-метрики "Recall @ FPR 5%" (0.648 против 0.646). Кроме того, гибридная модель показала меньшую стабильность на кросс-валидации.

Деплой тяжелой PyTorch модели ради улучшения метрики на 0.2% имеет отрицательный ROI из-за более высоких затрат на сервер и усложнения инфраструктуры. Поэтому для production API я выбрал базовую модель LightGBM. Это соотносится с лучшими практиками MLOps: низкий latency, легковесный Docker-контейнер и отсутствие необходимости во внешних Scalers/Imputers на этапе инференса.

## Технологический стек
- Инфраструктура: Docker Compose, PostgreSQL, FastAPI, Redis
- Машинное обучение: PyTorch, LightGBM
- MLOps и трекинг: MLflow, Optuna

## Чему я научился
1. Решил проблему нехватки памяти при загрузке тяжелых признаков за счет SQL-чанкинга (`chunksize`), понижения размерности типов данных (`float64` в `float32`) и ручного вызова garbage collection.
2. Решил проблемы с macOS (OpenMP segmentation faults) при конфликте LightGBM и PyTorch, а также изолировал конфликты проброса портов на macOS.
3. Научился предотвращать утечку данных во времени, использовав временное разбиение на train/test. Теперь транзакции из будущего никогда не используются для обучения модели на прошлых данных.
4. Использовал Docker Compose overrides для настройки окружения (CPU/GPU) и настроил последовательность запуска контейнеров с помощью кастомных healthchecks.
5. Спроектировал PyTorch Autoencoder для обучения без учителя.
6. Использовал SHAP values для интерпретации предсказаний модели.


## Data Pipeline и Feature Engineering

**Порядок выполнения**
1. `src/scripts/create_table_script.py` - мигрирует сырые данные из CSV файлов в PostgreSQL.
2. `db/01_schema.sql` & `db/02_seed.sql` - инициализируют схему базы данных и заполняют ее исходными данными.
3. `db/03_train_features.sql` & `db/04_test_features.sql` - генерируют агрегаты с помощью оконных функций напрямую в БД.


В процессе миграции я объединил таблицы `train_transaction` и `train_identity` по `TransactionID`.

Моей первой поведенческой гипотезой было: `card1` = уникальный ID пользователя, `uid1`.
Я экспериментировал с более узкими псевдо-идентификаторами: `uid2 = card1_card2`, `uid3 = card1_card2_addr1`, `uid4 = card1_card2_addr1_Pemaildomain`.
Эти признаки привели к сильному переобучению, поэтому я удалил их и оставил более простое представление `uid1`.

Затем я рассчитал агрегаты по `uid1` с использованием скользящих окон (rolling-windows).

Примечание: Чтобы предотвратить утечку данных, я рассчитывал агрегаты скользящего окна от первого вхождения до строки, предшествующей текущей (`ROWS BETWEEN UNBOUNDED PRECEDING AND 1 PRECEDING`).

### Поведенческие гипотезы
Я выдвинул несколько гипотез и построил следующие агрегаты на базе `uid1`:
- Количество транзакций за последние 5м, 1ч, 24ч, 7д.
- Время с момента последней транзакции.
- Сумма транзакций за последний час.
- Отношение суммы текущей транзакции к средней транзакции пользователя.
- Время с момента последней смены геопозиции.
- Новизна устройства (отдельно для мобильных и десктопных девайсов).

Затем я провел легкий препроцессинг в Pandas (удалил колонки, где доля пропусков > 90%, отсортировал по времени транзакции).

Для предотвращения временной утечки использовалось разбиение Time series split для Train/Val/Test сетов.

## Моделирование: Autoencoder + LightGBM
Я реализовал два пайплайна обучения: LightGBM с добавлением автоэнкодера и только LightGBM (baseline).

Моей базовой моделью был LightGBM. Однако, чтобы помочь алгоритму улавливать аномальные паттерны, я добавил PyTorch Autoencoder (unsupervised). Он возвращает новую колонку `anomaly_score`, на которой затем обучается LightGBM.

#### PyTorch Data Preprocessing
Моя стратегия:
1. Выполнить One-Hot Encoding для строковых признаков.
2. Применить Imputing и Scaling для числовых признаков (заменить NaN на среднее и рассчитать std).
3. Сохранить список финальных признаков для инференса.
4. Сохранить Imputer и Scaler для инференса.

#### Автоэнкодер
Он использует для обучения метод "бутылочное горлышко" с настраиваемым параметром `latent_dim` (самая узкая часть).

## MLOps и настройка гиперпараметров
Я провел три этапа настройки гиперпараметров (HPO):
1. PyTorch HPO. Поиск лучших гиперпараметров для PyTorch Autoencoder (включая `latent_dim`).
2. LightGBM HPO с признаками из PyTorch. Поиск гиперпараметров для LightGBM с использованием `anomaly_scores` из уже оптимизированного Autoencoder.
3. LightGBM HPO без признаков из PyTorch. 
После этого я сравнил метрики гибридного пайплайна (PyTorch+LightGBM) с базовым (LightGBM only).

## Выбор порога (Threshold Selection)
Я разработал два подхода для поиска оптимального порога с использованием `precision_recall_curve`:

### Бизнес-порог (Business-driven threshold)
Бизнес-требование состояло в том, чтобы максимизировать полноту обнаружения фрода (Recall), удерживая False Positive Rate (FPR) на уровне 5% или ниже.
Однако, если бизнес-цель недостижима, в качестве запасного варианта будет использоваться F1-оптимальный порог.

### F1-оптимальный порог
Использует формулу F1 и берет значения recall и precision из наилучшего соотношения F1.

## Мониторинг Data Drift (PSI)
Базовый мониторинг индекса стабильности популяции (PSI) был реализован через скрипт (запускается вручную), который рассчитывает PSI между train и test данными, а затем выводит признаки с наибольшим влиянием (если PSI > 0.1). Это помогает отслеживать деградацию модели в продакшене.

## Redis
Главным вызовом был расчет агрегатов для входящих транзакций в реальном времени. Расчет агрегатов в PostgreSQL работает слишком медленно и неприемлем для инференса, поэтому мне нужно было вычислять их на лету. Для этого я добавил в проект Redis, который извлекает агрегаты за время O(1) и O(log N).

### Прогрев кэша (Cache Warming)
Поскольку мне нужно было рассчитывать исторические агрегаты как для новых, так и для прошлых транзакций, я предварительно загрузил прошлые транзакции из SQL в Redis. Я написал SQL-запрос для выгрузки lifetime-статистики (время последней транзакции, количество транзакций, сумма всех транзакций). Я также сделал запрос для выгрузки всей информации о транзакциях и устройствах за последние 7 дней. Затем эти данные загружаются в Redis через pipeline.

### Расчет агрегатов на лету
- Перед добавлением новой транзакции я читаю время последней транзакции (`hget`, `hset`).
- Добавляю сумму транзакции к общей сумме (`hincrbyfloat`).
- Для проверки новых устройств я использую сигнатуру `devicetype:deviceinfo` и просто проверяю ее наличие (`sismember`). После этого я создаю zkey `devicetype:deviceinfo: timestamp` для расчета времени с момента последней смены геопозиции.
- Скользящие окна рассчитываются через `zrange` с различными диапазонами.
- Также я сохраняю zkeys `transaction_id:transaction_amt: now` и затем вычисляю сумму транзакций за последний час средствами Python.

### Выгрузка данных обратно в SQL
Я реализовал эту функцию через мануальный скрипт, который можно запускать по требованию (например, в часы минимальной нагрузки).
Когда Redis получает новую транзакцию, он копирует ее в список `manual_tx_queue`. Мой скрипт забирает эти данные, кладет их в PostgreSQL и очищает очередь. Извлечение реализовано через `lrange`, очистка — через `ltrim`.

## API
Приложение FastAPI использует контекстный менеджер **lifespan**. При запуске сервис загружает веса моделей и JSON-метаданные в оперативную память.

### Эндпоинт /healthcheck (GET)
Это асинхронная функция.

1. Она использует асинхронный движок `asyncpg` и пытается выполнить внутри базы данных: `SELECT 1;`
2. Она проверяет, что веса моделей были успешно загружены в память.

### Эндпоинт /predict (POST)
Эндпоинт защищен зависимостью от API-ключа. Pydantic валидирует схему входящей транзакции до того, как она попадет в сервис инференса. Затем входные данные и метаданные отправляются в сервис `process_payment`.

### Сервис process_payment
Имеет подфункцию `apply_business_rules`: простые правила, написанные бизнесом, которые гарантированно ведут к блокировке (fraud alert). Например, если сумма транзакции > 500 000 и она была совершена с нового устройства, возвращается: "Blocked by Rule: Huge amount from new device" и срабатывает алерт.
ML пайплайн инференса запускается только в том случае, если транзакция прошла бизнес-правила.

### Graceful Degradation (Плавная деградация)
Если ML инференс становится недоступен по какой-либо причине, срабатывает fallback-функция плавной деградации, содержащая простые правила.

## А что, если бы я использовал PyTorch в инференсе?
Я бы загружал файлы `num_imputer` и `scaler` во время запуска FastAPI. Затем применял бы OHE для строковых значений новой транзакции. Для числовых значений я бы сначала заменял пропуски средними значениями (из Imputer), а затем применял z-score ко всем числовым фичам. Важно отметить, что последним шагом перед инференсом PyTorch была бы переиндексация признаков с использованием сохраненного списка `final_pytorch_features`.

## Ограничения и известные проблемы проекта
#### Локальный запуск на macOS: SIGSEGV при запуске LightGBM после PyTorch
На macOS PyTorch и LightGBM поставляются со своими собственными средами выполнения OpenMP (`libomp`), что вызывает segfault (ошибку сегментации), когда оба фреймворка используются в одном процессе.
Моим первым решением было ограничить `num_threads=1` для LightGBM на macOS, что отключает конфликтующую инициализацию OpenMP. Однако в итоге я решил не допускать локальный запуск этого проекта, разрешены только запуски через Docker (Linux) с полной многопоточностью.
